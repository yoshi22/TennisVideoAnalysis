# 2026-09-12: 方針転換 — VLM自動ラベリング + RF-DETR + ショット毎コーチング

## 背景・きっかけ

X の @fujitech_ai(すたーまん, 9/10 投稿)の個人開発を起点に、CV アプローチとプロダクトの北極星を見直す。

### 起点 post の核心(原文から確定)
- 入力は **iPhone で撮った動画だけ**。そこから「ボール速度 / フォア・バック判別 / コース(着地位置)/ 打点時の体の位置」を取得。
- **ラベリングは大型 VLM(Astra = GPT-6)に肩代わりさせる**。実検出は **RF-DETR を fine-tuning** した軽量モデル。
- 設計思想:「CV で一番コストがかかるのはアノテーション。**賢いモデルで教師データを作り、小さいモデルを走らせる**」。
- RF-DETR は Roboflow のリアルタイム検出・**Apache 2.0・エッジサイズ**。**将来的に iPhone 上で完結**させる前提に筋がいい。
- ゴール: 練習を記録 → 経時で上達を追う → 技術改善フィードバック。

## なぜ当プロジェクトに効くか

現行 CourtLens の 2 大ボトルネックに直撃する:

1. **検出精度の頭打ち**: ブロブ/モーション・ヒューリスティック(`src/services/ball/core/rallySegment.ts`)は最良 eventF1 ≈ 0.43–0.49。ゲート 0.85 に遠い。失敗モードは「影・隣コート・グレアとボールを分離できない」(`docs/development-logs/03_ai_analysis_roadmap.md`)。→ **自前データで fine-tune した物体検出器**が直接効く領域。
2. **データ/ラベリング律速**: arm2 は「固定カメラ ~30 本必要・現状 8 本」で手動ラベリング律速。→ **VLM 自動ラベリング**でアノテーションコストを肩代わり。

※ 過去の TrackNet V1 却下(F1 0.225, `20260522_phaseB_ball_tracking.md`)は *事前学習モデルのゼロショット*であり、本件(自前データで fine-tune)とは別物。

## 段階ロードマップ(最小リスクから)

- **Phase 0**(最安・最重要): 十数枚のフレームに VLM で ball/racket/court/player の box を付け、手動ラベルと IoU 比較。**ボール box 品質で Go/No-Go**。
- **Phase 1**: 自動ラベルで RF-DETR を fine-tune、mAP 評価。既存ブロブとの A/B。

- **Phase 4**: アプリ統合。ショット毎出力を draft `PointRecord` へ、レポートをショット毎コーチングへ再設計、姿勢機能を統合。

## 実証ログ(2手法とも「遠景・固定・720p ではボール不可」)

### Phase 0 — 単一フレーム VLM プローブ(Claude Vision, 実施済)
`yt-maitou-suzumura-muko-clip1`(30fps, 1280×720)のプレー中5枚:
- コート隅/ライン ◎、選手 ○〜◎、ラケット △、**ボール ✗(数〜十数px・飛球ブラーで目視も不可)**。
- fps マッピング確定: `frame_N ≈ N/30秒`。

### Phase 0.5 — ブロブ候補生成(実装 & 実行、実施済)
新規スクリプト(既存 blob ロジックを box 出力に拡張して再利用):
- `scripts/eval/autolabel/blob_candidates.py`: motion diff + `remove_large_regions` + 連結成分。定数は `blobDetect.ts`/`score-blob-anchor.py` と一致。
- `scripts/eval/autolabel/generate.py`: クリップ+区間で候補 JSONL + デバッグオーバーレイを出力。
- 実行(ラリー1, 11–27s, 481フレーム): 候補ありフレーム 60%・平均 2.5個/フレーム。
- **オーバーレイ目視結果**: 候補は**ほぼ全て手前選手の動く体部位**(頭/腕/ラケット/脚/シューズ)に集中。**ボールは分離できず**。
- **原因**: `remove_large_regions` は連続シルエット塊は消すが、動く選手のフレーム差分が生む**輪郭断片**が多数ボールサイズ/形状フィルタを通過。ラリー検出は「数える」だけなので問題化しないが、**ラベリング(=ボール分離)には構造的に不向き**。

### 結論(重要)
- Phase 0(VLM)と Phase 0.5(ブロブ候補)の**両方**が、この**遠景・固定・720p 素材でボールを取れない**ことを実データで確認。
- → **ボール系指標(速度/コース)のボトルネックは手法ではなく素材(解像度・画角)**。
- **一方で非ボールクラス(コート/選手/ラケット)は VLM で容易**(Phase 0 で確認)。

### 前進の2経路(要オーナー判断)
- **経路A(非ボール先行)**: 既存コーパスで VLM(Astra/Claude)により court/player/racket をラベル → RF-DETR 学習 → **姿勢ベースのストローク・コーチング + コート/選手アナリティクス**を先に提供。ボール依存指標(速度/コース)は延期。
- **経路B(高解像度素材)**: 至近・高解像度クリップを取得(post と同条件)。ボールが十分大きく単一フレーム VLM でラベル可能に → ボール系指標を解禁。

## 経路B(ボール軌道追跡)feasibility 評価 — 結論: **実現可能**

### 重要な訂正: 「素材がボトルネック」→「単一フレーム手法がボトルネック」
Phase 0/0.5 は**単一フレーム手法**(VLM・ブロブ)を試して失敗した。だが TrackNet 系研究の一次データは別の絵を示す:
- **TrackNet の学習データは 1280×720 @ 30fps(=我々のコーパスと同一)**、**ボール平均直径 5px でも追跡成功**。ボールは「5〜15px 物体」として設計され、位置誤差スペックも 5px。
- つまり **720p/30fps・5px ボールは TrackNet 系(複数フレームのヒートマップ)なら追跡可能**。5px ボールが単一フレームで無理なだけ。
- 我々の過去 TrackNet V1 失敗(F1 0.225)は**ゼロショットのドメインギャップ(放送→固定)**であって解像度ではない。**ファインチューンは未検証の有望路**。

### なぜ我々の試行は失敗したか(いずれも「B が不可能」を意味しない)
1. 単一フレーム(VLM/ブロブ)は 5px ボールを原理的に取れない → **時間的手法が必須**。
2. コーパスが **YouTube 再ダウンロード = 再圧縮**で、数pxのボールがコーデックに潰される(生撮影より不利)。
3. TrackNet V1 は**ゼロショット**(未ファインチューン)。

### 現実的な動画品質要件(B を成立させる下限)
- **解像度**: 1080p が快適な下限、720p は端(TrackNet 学習解像度だが余裕小)、4K は良好。
- **fps**: 30 で可(TrackNet 既定)、**60+ 推奨**(モーションブラー減・軌跡が密)。iPhone 60/120fps が理想。
- **ビットレート/圧縮**: **最重要**。生撮影・高ビットレートを維持し、**YouTube 経由の再圧縮を避ける**。
- **カメラ**: 固定三脚・後方やや高所・コート全体を画角に。近い/高解像度ほどボールpx増(post は courtside iPhone)。
- **照明**: 明るい日中(実効シャッター速く、ブラー減)。

### B の正しい手法
- **時間的ヒートマップ型ボールトラッカー(TrackNet V2/V3/**V4**・WASB・TOTNet)を in-domain でファインチューン**。単一フレーム検出(VLM/ブロブ/素の RF-DETR 単フレーム)ではない。
- post の「fine-tuned RF-DETR」は**至近でボールが十分大きい(≥15-20px)前提**なら成立。遠景なら TrackNet 系が適。
- 参考: 単眼テニス Hawk-Eye 論文(arXiv:2511.04126)は custom YOLOv5 で **ball 89% mAP**、コートは ResNet50 で14点。「データは量より質・一貫した画角が重要」と明記。AceSense はスマホ上でボール追跡を製品化(on-device 可能性の傍証)。

### 一次ソース(X 実読・syndication/fxtwitter 経由)
- **@measure_plan (AA)** = 英語の原典ビルダー(fujitech=すたーまんが翻訳・言及した元)。iPhone 動画 → fine-tuned RF-DETR で ball速度/FH-BH/コース/打点。**B は実在で成立**。
- **@LearnOpenCV (Satya Mallick, 9/7)** = GPT-6 Astra Ultra でテニスボールをアノテーション成功。ただし**「印象的だが catch がある」= コスト**: ボールアノテーションに3並列エージェントで 8m35s・17,611トークン、全体 11m49s・30,481トークン、**累計 7.87M トークン(uncached 313,914 + cached 7,528,320、フレーム検査呼び出しで文脈再利用)**。
  - 含意1: **VLM ボールアノテーションは"複数フレーム/エージェント的検査"なら成功する**(私の Phase 0 単一フレーム失敗と矛盾しない=手法差)。
  - 含意2: **大型 VLM でのボールラベリングは1クリップでも数百万トークン級=高コスト**。→「賢いモデルで教師作成→小型で推論」の"教師作成"は**少量に絞る**か、候補検出器+VLM検証でトークンを抑える設計が要る。

### B の最安デリスク実験(データ campaign 前に)
1. **既存 720p コーパスで TrackNet をファインチューン** → ゼロショット 0.225 を超えるか(=ドメインギャップ説の検証)。
2. 並行で **1080p/60fps・生撮影の小コントロールセット**を1-2本用意 → 品質ヘッドルームを測る。
- この2つで「手法(ファインチューン)」と「素材(高品質生撮影)」の寄与を分離できる。

## Phase B0 進捗 — ゼロショット TrackNet が実データでボールを当てている(決定的)

既存のゼロショット TrackNet V1 出力(`eval/datasets/fixed-camera-v2/ball-tracks/tracknet-v1/yt-maitou-suzumura-muko-clip1.jsonl`, stride4/7.5fps, visible19%)を実フレームに重畳検証:

- 結論: **rally-F1 0.225 は窓化の副産物**で、per-frame ボール検出は良好。**ファインチューンで大幅改善が見込め、ゼロショットは GT prelabel に使える**。
- 環境確認: torch 2.2.2 + **MPS 利用可(ローカル無償学習可)**。TrackNet 重みはローカル未保存(要 `--download-weights`)。v2 クリップ動画7本残存(30fps 再抽出可)。

→ B0 の GT ブートストラップ(prelabel+手動修正)は現実的。次: GT 土台整備 → 学習コード新設。

## モデル選定確定(RF-DETR 主 + TrackNet 教師)

TrackNet V4 vs RF-DETR を調査し決定:
- **TrackNet V4**: ICASSP2025、公式TF + PyTorch実装(AIKnowU)あり。だが **PyTorch実装はライセンス無表記=商用不可リスク**、**事前重み未配布**、V2土台+V4融合の組立要。入力3連フレーム288×512、ラベルは点(Frame,Visibility,X,Y)。
- **RF-DETR**: `roboflow/rf-detr` **Apache 2.0**、COCO事前重み+turnkeyファインチューン、エッジ設計。テニスボール **mAP@50 59.9%**(85枚・30-45分)。単フレームで5pxボールは中程度。
- **決定: RF-DETR 主(出荷/エッジ)+ TrackNet 教師(GT生成)**。理由=ライセンス(商用可)+on-device+ツール。RF-DETRの単フレーム弱点は「TrackNet教師でGT生成」「推論時トラッカー+補間」「Phase B1で撮影品質向上」で補う。TrackNet→RF-DETR はアーキ違いの**教師蒸留**(自己蒸留ではない)。

## Astra 利用可否確定
- GPT-6 Astra = OpenAI最新(2026-09)。**ChatGPT Plus/Pro契約は対話利用のみ**。自動ラベリングは **OpenAI API(別課金)** か **Roboflow**。API価格 入力$10/1M・cached$1/1M・出力$50/1M → LearnOpenCV実測≒**$12/クリップ**(安価)。
- **結論: Astra は任意ブースター**。GT主生成は無償TrackNet教師。**精度不足時のエスカレーション**(Step2=難所のみAstra→Step3=面的Astra→Step4=撮影品質向上)を計画に明記。

## Phase B0 続報 — RF-DETR は微小球で頓挫、but 時間軸(軌跡)で TrackNet が有効と実証

### RF-DETR ローカル学習の結果(不適)
- 依存地獄を突破(隔離 venv: rfdetr 1.5.2 + transformers 4.57 + torch 2.2.2 + numpy<2)、COCO 化・学習まで到達。
- **しかし解像度320では ball mAP=0**。原因は **ball(~5px)< ViT パッチ(16px)=サブパッチで transformer に見えない**。学習loss は下がるが検出不可。RF-DETR で当てるには解像度~1024+ が要る(ローカルはメモリ的に非現実、Modal 級)。
- 教訓: **微小球には ViF パッチ型(RF-DETR)より CNN ヒートマップ型(TrackNet)が構造的に適する**。

### 単フレーム評価の誤り → 時間軸評価が正解
- ゼロショット TrackNet の高信頼検出を per-frame 目視すると曖昧・誤検出(フェンス等)混在。だが **これは"見る角度"の誤り**。
- **軌跡(時間リンク+外れ値棄却+内挿)で見ると、滑らかなボールの弧が明確に出る**(rally13=放物線、rally1=サーブ弧、rally4=往復)。誤検出は軌道から外れて自動棄却。
- 実装は **codex(MCP)に委譲**しトークン節約: `scripts/eval/autolabel/{viz_trajectory,trajectory_process}.py`。muko-clip1 で raw 402 visible → kept 165 + interp 697、被覆 10.4%(7.5fps 入力ゆえ疎。手法でなく入力の限界)。出力: `ball-tracks/tracknet-v1/clean/`。
- **結論: 「動画=軌跡として捉えれば、既存720p素材でボール検出は成立する」**。密度は stride1(30fps)再推論で解決可能。GT も軌跡検証で作れる(単フレームのピン留め不要)。

### モデル方針の更新（B0 実証を受け）
- **検出器は TrackNet(V1 で着手→V4 が精度天井)**。RF-DETR は微小球で不適のため主検出から外す(高解像度/近接素材なら再検討可)。
- ライセンス: アーキはリポ内・自前学習で回避可。研究段階は問題なし。
- **精度の最大レバーはモデル世代でなく「入力品質＋データ量」**(現行720pが天井を規定)。
